# Release checklist for version 0.1.1 (the fixes after review; the engine 0.1.1 must be on PyPI first)

Order: **1.** publish the engine 0.1.1 · **2.** the release commit of the app · **3.** the tag · **4.** the submission. Status on 10 Nov 2026: the engine 0.1.0 is on PyPI (the tag `engine-v0.1.0`, 9 Nov 2026) and cannot be changed. The engine 0.1.1 and the app 0.1.1 (version, the exact pin `ai-munimji-engine==0.1.1`, the fixes) are prepared on branches and not merged; CI of the app fails until the engine 0.1.1 is on PyPI. The app is not tagged and nothing is submitted. The app's 0.1.0 was never tagged or submitted, so 0.1.1 is the first release.

1. **The engine first** (repository erpnext-ai-agents, `docs/PUBLISH_ENGINE.md`): merge its pull request, tag `engine-v0.1.1`, approve the `pypi` environment, then check `pip install ai-munimji-engine==0.1.1` in a clean environment. **To do.**
2. **The release commit** (through a pull request, CI green once the engine is on PyPI). The exact edits, done on the branch:
   - `ai_munimji/__init__.py`: `__version__` is `"0.1.1"`. `CHANGELOG.md`: the heading "0.1.1 (date)" holds the fixes after review.
   - The wording "in development / not released / early stage": `README.md` line 3, `hooks.py` (`app_description`), `pyproject.toml` (`description`), `docs/INSTALL.md` line 3, `docs/KNOWN_LIMITATIONS.md` line 3, `dev/new-app.sh` line 19. Nothing may say "on the Marketplace" before the review has approved it.
   - The engine's source: `pyproject.toml` pins `ai-munimji-engine==0.1.1`; `README.md` ("The engine"), `dev/README.md` and `docs/INSTALL.md` say that it comes from PyPI and that a local wheel is the development route.
   - CI: `ci.yml` and `linter.yml` install the pin that `pyproject.toml` holds from PyPI (the composite action `engine-wheel` is gone). The repository variables `ENGINE_REF` and `ENGINE_REPO` are no longer read by anything; deleting them is still to do.
   - `docs/LISTING.md` (section 1): the registry file's `version` is `0.1.1`; its `commit` is the SHA that `main` has after the merge, which exists only then.
3. **Tests that change with it:** `tests/test_docs.py` (the version it pins is 0.1.1). `locale/main.pot` is regenerated by the gate. The gate ran on the branch with the engine's 0.1.1 wheel installed locally; `verify-all.ps1 -Fresh -WithRest` has to run on the release commit.
4. **The tag:** `v0.1.1` on the release commit, CI green on it. Frappe Cloud makes a release from each push to the branch, not from a tag (docs.frappe.io, "Publishing an App to Marketplace", page dated 24 Oct 2026); the tag is for people and for CI.
5. **Before submitting:** the repository is public; the private-bench trial is done (install, switch on, one request, approve, uninstall); screenshots and the demo video are made; `docs/PRIVACY.md`, `TERMS.md`, `SUPPORT.md`, `USER_GUIDE.md` have their placeholders filled ("[your name]", links, governing law).
6. **Frappe Cloud, dashboard route** (same page): Settings, Profile, "Become a Publisher"; Marketplace, New App, "Add from GitHub", the repository and branch; "Complete Listing": logo (square, at least 200 px, no text), the five links (Website, Support, Documentation, Terms of Service, Privacy Policy), a summary of 40 to 80 characters that does not repeat the name, a long description without installation steps, screenshots; then **Versions, Show Releases, Submit** on the release of the release commit ("Awaiting Approval"); then **Mark app ready for review** ("In Review"; the page says up to 10 days, the team may ask for a short demo video, and the Audit Reports tab shows the automated results).
7. **The other route:** a post on discuss.frappe.io dated 10 Sep 2026 describes a registry on GitHub (`frappe/marketplace`: an entry in `apps.json` and a file `apps/<app>.json`, opened as a pull request, commit-based releases, automated checks instead of manual approval) for Frappe Cloud v2 and pilot, partly live. Check which one applies to you the day you submit.
8. **Before the release that adds Telegram** (written 13 Nov 2026; Telegram is on `main` after 0.1.1 and is not released). Do these on the release commit, in addition to the steps above:
   - **The text says what the code does.** Read `docs/PRIVACY.md`, `docs/TERMS.md`, `docs/SUPPORT.md`, `docs/USER_GUIDE.md`, `docs/TELEGRAM.md`, `docs/LISTING.md` and the README against `ai_munimji/tests/test_nothing_leaves.py` (it names the one module that reaches the network) and `tests/test_rules.py` (it names the one method open to guests and the places that act as someone else). Search every public file for the old claims: "sends nothing", "no data", "nothing leaves", "no e-mail", "no secrets", "no message". Each must say "by default", or name Telegram, or still be true as written.
   - **The three descriptions on the Settings page** (expiry, reminders, stock alerts) and the two in "Keep logs for (days)" agree with `docs/KNOWN_LIMITATIONS.md`; `locale/main.pot` is regenerated.
   - **A run with a real bot**, once, on a private bench: make a bot with @BotFather, switch Telegram on in each mode (webhook on a public HTTPS address, polling with two `long` workers), connect a chat (also by typing `/start` and the code, as on a network that blocks `t.me`), answer a request in Telegram and in the Desk, switch Telegram off, then revoke the bot. The pretend Telegram (`dev/telegram-e2e.ps1`) proves the app, not Telegram.
   - **The engine** pin in `pyproject.toml` is the engine release that holds the Telegram channel (0.1.3 or later), and it is on PyPI before the app's CI runs.
   - **The listing:** the screenshots of Telegram show fictional items and a fictional chat, no real bot token, chat number or name (`docs/LISTING.md`, section 4); the registry description needs no change.

# Release checklist for version 0.2.0 (Telegram, and the fixes of the production-readiness review)

Order: **1.** the engine · **2.** the release commit of the app · **3.** the checks on it · **4.** the tag · **5.** the registry file · **6.** the submission. Status on 13 Nov 2026: the engine 0.1.3 (the Telegram channel) is on PyPI (the tag `engine-v0.1.3`, 12 Nov 2026) and cannot be changed. The app's 0.2.0 is prepared on a branch and not merged, not tagged, and nothing is submitted. The tag `v0.1.1` was made on 10 Nov 2026 and that release is not submitted: it has neither Telegram nor the fixes of the production-readiness review, and the pages the listing links to describe both. The first version to submit is 0.2.0.

1. **The engine first.** Done: the engine 0.1.3 is on PyPI and the app pins it exactly in `pyproject.toml`. CI installs that pin from PyPI on every run, so a missing or wrong engine fails the build.
2. **The release commit** (through a pull request, CI green). The exact edits, done on the branch:
   - `ai_munimji/__init__.py`: `__version__` is `"0.2.0"`. `CHANGELOG.md`: the heading "0.2.0 (date)" holds what is new, and says how to upgrade from 0.1.1.
   - The pages that name the version say 0.2.0: `README.md`, `docs/INSTALL.md`, `docs/KNOWN_LIMITATIONS.md`, this page, `docs/LISTING.md` (the registry file's `version`). The prose "version 0.2" in the privacy policy, the terms, the user guide and the limitations. `tests/test_docs.py` pins the version and fails on a page that names another.
   - The wording "in development / not released / early stage" is in no page that describes the app (`README.md`, `hooks.py`, `pyproject.toml`, `docs/INSTALL.md`, `docs/KNOWN_LIMITATIONS.md`, `dev/new-app.sh`; the test reads them). Nothing may say "on the Marketplace" before the review has approved it.
   - The engine's source: `pyproject.toml` pins `ai-munimji-engine==0.1.3`; `README.md` ("The engine"), `dev/README.md` and `docs/INSTALL.md` say that it comes from PyPI and that a local wheel is the development route.
3. **The checks on the release commit.**
   - CI green on the merge commit on `main`: the four required checks. CI installs the newest Frappe 16 and ERPNext 16 each time, so it can fail without a change here (it did on 13 Nov 2026, when a newer ERPNext refused a supplier in a group supplier group); read the failure before blaming the commit.
   - `locale/main.pot` is regenerated (`dev/scripts/make_pot.py`); the gate and CI check it.
   - `verify-all.ps1 -Fresh -WithRest` runs from nothing on the release commit (25 to 42 minutes), and `dev/check-uninstall.sh` (install, two migrates, uninstall, install again).
   - **The upgrade from 0.1.1:** `dev/check-upgrade.sh` (about 5 minutes). On a throw-away site it installs the code of the tag `v0.1.1`, sets what a person would have set, then switches to the code of the working tree and runs `bench migrate` twice. It requires: the settings, the stock check's schedule and the running jobs are as they were; the Telegram settings, the Munimji Telegram Link DocType and the Telegram housekeeping job (stopped) appear and Telegram is off; nothing the old version had is gone; the second migrate changes nothing. It passed on 13 Nov 2026 against this branch, and was shown to fail when Telegram is left on, when the person's schedule is changed, and when the Telegram job is left running. It checks a migrate that works; a migrate that fails half way is not rehearsed, and a downgrade is not tested (the way back is the backup that `bench update` takes).
4. **The tag:** `v0.2.0` on the release commit on `main`. Frappe Cloud makes a release from each push to the branch, not from a tag (docs.frappe.io, "Publishing an App to Marketplace", page dated 24 Oct 2026); the tag is for people and for CI.
5. **The registry file** (`docs/LISTING.md`, section 1): `version` is `0.2.0`; `commit` is the full SHA that `main` has after the merge, which exists only then; `frappe_core` is copied exactly from `pyproject.toml`. Run the registry's own check locally against that commit (clone `frappe/marketplace`, see its `docs/marketplace-check`) and read what it says about the webhook, the app's one method open to guests: the registry's Semgrep rule lists such a method as a warning for a person to review, and the code carries a `nosemgrep` with the reason.
   - **Run on 13 Nov 2026** against the tip of the release branch (commit `a7704f0`, before this note), on an export of it: the schema, the truthful-metadata check (the Frappe branch it installs on is `version-16` only), the Semgrep scan (0 findings, 0 blocking) and all ten checks of Pilot's app validator pass, and Pilot's dependency resolution from the real PyPI passes (`ai-munimji-engine==0.1.3`). The registry's rules had not changed since the run of 10 Nov; Pilot's validator had.
   - **Not run:** the clone at the exact commit (it needs the pushed commit) and the install into a Pilot-made bench (it needs a systemd host). The app builds no assets, so the memory limit of that build does not apply.
   - **What the comments hide:** the registry honours `nosemgrep`. With every comment ignored its rules report 14 findings: the webhook as a method open to guests, 4 manual commits (`jobs.py`, `stores/locks.py` twice, `telegram/jobs.py`) and 9 `set_user` calls (the queued jobs, the webhook after the secret is proved, a press acting as the person whose chat it is). Each carries its reason in the code, and `tests/test_rules.py` allows each in a named function only.
   - **Repeat it on the merge commit on `main`**, and keep the result with the release.
6. **Before submitting:** the repository is public; the private-bench trial is done (install, switch on, one request, approve, uninstall); screenshots and the demo video are made; `docs/PRIVACY.md`, `TERMS.md`, `SUPPORT.md`, `USER_GUIDE.md` have their placeholders filled (done on 13 Nov 2026) and a qualified person has read the privacy policy and the terms, which say that they are not legal advice.
7. **Frappe Cloud, dashboard route** (same page): Settings, Profile, "Become a Publisher"; Marketplace, New App, "Add from GitHub", the repository and branch; "Complete Listing": logo (square, at least 200 px, no text), the five links (Website, Support, Documentation, Terms of Service, Privacy Policy), a summary of 40 to 80 characters that does not repeat the name, a long description without installation steps, screenshots; then **Versions, Show Releases, Submit** on the release of the release commit ("Awaiting Approval"); then **Mark app ready for review** ("In Review"; the page says up to 10 days, the team may ask for a short demo video, and the Audit Reports tab shows the automated results).
8. **The other route:** a post on discuss.frappe.io dated 10 Sep 2026 describes a registry on GitHub (`frappe/marketplace`: an entry in `apps.json` and a file `apps/<app>.json`, opened as a pull request, commit-based releases, automated checks instead of manual approval) for Frappe Cloud v2 and pilot, partly live. Check which one applies to you the day you submit.
9. **Telegram, on this release.** In addition to the steps above:
   - **The text says what the code does.** Read `docs/PRIVACY.md`, `docs/TERMS.md`, `docs/SUPPORT.md`, `docs/USER_GUIDE.md`, `docs/TELEGRAM.md`, `docs/LISTING.md` and the README against `ai_munimji/tests/test_nothing_leaves.py` (it names the one module that reaches the network) and `tests/test_rules.py` (it names the one method open to guests and the places that act as someone else). Search every public file for the old claims: "sends nothing", "no data", "nothing leaves", "no e-mail", "no secrets", "no message". Each must say "by default", or name Telegram, or still be true as written. Done on 13 Nov 2026.
   - **The descriptions on the Settings page** (expiry, reminders, stock alerts, "Keep logs for (days)") agree with `docs/KNOWN_LIMITATIONS.md`. Done on 13 Nov 2026.
   - **A run with a real bot**, once, on a private bench: make a bot with @BotFather, switch Telegram on in each mode (webhook on a public HTTPS address, polling with two `long` workers), connect a chat (also by typing `/start` and the code, as on a network that blocks `t.me`), answer a request in Telegram and in the Desk, switch Telegram off, then revoke the bot. The pretend Telegram (`dev/telegram-e2e.ps1`) proves the app, not Telegram. Polling was run with a real bot on 12 and 13 Nov 2026. **Webhook mode was run against real Telegram on 13 Nov 2026** on a Frappe Cloud site (the `main` branch at commit `79798bc`; the same code as 0.2.0, which changes the version number, documents and development tools only): 11 messages sent, 8 updates received, 5 requests decided from Telegram (and a draft Purchase Order made from them), 5 in the Desk, no error logged; the public address refused every call without the secret. What that run covers and what it does not is in `docs/KNOWN_LIMITATIONS.md` ("How far it has been tried"); the listing says no more than that. **Repeat a short run on the release commit itself** once it is merged (switch Telegram on, one stock check, one button press), because the run above was on `main` before the release commit existed.
   - **The listing:** the screenshots of Telegram show fictional items and a fictional chat, no real bot token, chat number or name (`docs/LISTING.md`, section 4); the registry description needs no change.
